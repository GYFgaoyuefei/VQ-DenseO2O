# Efficiency Evaluation Protocol

以下英文段落可用于论文方法部分；当前真实指定GPU实验为NOT RUN。获得完整真实记录后再搭配结果表使用，不应把方法描述当作已完成实验的证据。

All models, including the five independent configurations and four combination ablations, are evaluated using a single efficiency measurement program following the PyTorch FP32 deployment protocol established in the standard_ablation_test experiments on October 17, 2026. Measurements use an NVIDIA RTX PRO 6000 Blackwell Server Edition GPU with the PyTorch eager evaluation/deployment backend, batch size one, and a GPU-resident all-zero FP32 input tensor of shape 1 × 3 × 640 × 640. Automatic mixed precision and TF32 are disabled. Each of the three training seeds (0, 42, and 3407) is evaluated with five repetitions; each repetition contains 100 warm-up iterations followed by 500 timed iterations for each measured scope. Latency is measured with Python's high-resolution wall clock, with CUDA synchronization immediately before and after every iteration. The primary latency includes both the detector forward pass and the tensor-based postprocessor. Detector-only and postprocessor-only latencies are measured independently; their sum is not used as a substitute for the directly measured primary latency. Postprocessing uses the native deployment implementation with 300 selected predictions. Image I/O, preprocessing, data loading, host–device transfers, training losses, GR-VQ training computations, LI-CopyBlend augmentation, and COCO evaluation are excluded.

For each seed, the mean latency is first computed over the five repetitions. We report the mean and sample standard deviation across the three seed-level means. FPS is calculated as 1000 divided by the corresponding mean latency in milliseconds, rather than by averaging FPS values. P50 and P95 latencies are computed within each repetition using the median and nearest-rank 95th percentile, respectively, and summarized with the same repetition-then-seed averaging procedure. Peak allocated GPU memory is measured separately for each scope after resetting the peak statistic following warm-up; resident model and input allocations are included. Both the full detector parameter count before deployment conversion and the deployed parameter count are recorded, with the latter reported as Params(M) in the main table. GFLOPs cover only the deployed detector forward pass and are analyzed consistently using calflops after latency measurement. The tool version, counting convention, scope, and available operator-coverage evidence accompany the results. Counts with unverified or unsupported operator coverage are explicitly marked PARTIAL and are not presented as complete, exact FLOP counts; unavailable or failed analyses are left unreported. The same software versions and timing settings are required throughout a measurement campaign.
